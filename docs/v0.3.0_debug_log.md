# v0.3.0 Debug Log & Issue Resolutions

This log documents the tricky UI and styling issues encountered during the development of v0.3.0 and how they were systematically resolved.

## 1. KaTeX Math Equation Styling
*   **The Problem:** The KaTeX math formulas were rendering the correct characters but the alignment, sub/superscripts, and fractions were completely mangled.
*   **The Root Cause:** VS Code Webviews have a strict Content Security Policy (CSP). The `style-src` was configured with a `nonce`. In modern browsers, using a nonce disables the `'unsafe-inline'` fallback. Since KaTeX relies heavily on injecting inline `style="..."` attributes for precise character positioning, the browser silently blocked all of KaTeX's layout styles.
*   **The Fix:** Removed the `nonce` requirement from the `style-src` directive in `WebviewSecurity.ts`, allowing `'unsafe-inline'` styles to execute properly. KaTeX now renders beautifully.

## 2. Fullscreen Image Lightbox Positioning
*   **The Problem:** Clicking an image to open the lightbox zoom resulted in the image appearing in the bottom-right corner, off-center, or misaligned with the backdrop.
*   **The Root Cause:** A well-known CSS trap. The lightbox was using `position: fixed` to overlay the entire screen. However, the `body` tag had `max-width`, `margin: 0 auto`, and `transform` applied to it for centering the main content. In CSS, applying a `transform` or `perspective` to an element creates a new containing block for all its descendants, overriding `position: fixed` to anchor to the `body` instead of the browser viewport.
*   **The Fix:** Refactored the DOM structure. Moved all layout constraints (`margin`, `max-width`, `animation`) off the `body` tag and onto a new `.mv-main-wrapper` div. This freed the `body` to act as a pure viewport container, allowing the `position: fixed` lightbox to center perfectly.

## 3. Toolbar and Find Bar Overlap
*   **The Problem:** The Find Bar (`Ctrl+F` search input) and the floating Toolbar (TOC & Search toggle buttons) were visually colliding when the search bar was open.
*   **The Root Cause:** Both elements were absolutely positioned to the top right of the screen. The Toolbar occupied roughly `18px` to `80px` from the right edge, while the Find Bar was set to spawn at `right: 60px`, resulting in a direct collision.
*   **The Fix:** Adjusted `.mv-find-bar` to `right: 104px` in `preview.css`, ensuring it safely clears the toolbar buttons when it drops down.

## 4. TOC Sidebar Close Button Overlap
*   **The Problem:** When the Table of Contents sidebar was opened, an `✕` icon appeared to perfectly overlap the Search button (magnifying glass) in the toolbar, creating a confusing visual glitch.
*   **The Root Cause:** Z-index stacking collision. The `.mv-toolbar` had a `z-index` of `100`, while the `.mv-toc-sidebar` had a `z-index` of `90`. When the sidebar slid open, the transparent toolbar floated *on top* of the solid sidebar. The sidebar's `✕` close button (in `.mv-toc-header`) happened to align perfectly underneath the toolbar's search button.
*   **The Fix:** Bumped the `.mv-toc-sidebar` `z-index` to `120`. It now slides correctly over the toolbar, completely hiding the buttons beneath it.

## 5. Main Content Layout Shifting (TOC Toggle)
*   **The Problem:** Opening the TOC pushed the main document far to the left. Closing the TOC caused the document to get permanently stuck on the right side of the screen instead of returning to the center.
*   **The Root Cause:** The JavaScript toggle was injecting an inline style `margin-right: 0` when closed. Inline styles override CSS classes, completely breaking the `margin: 0 auto` declaration that was keeping the document centered. Additionally, adding any margin/padding shift when there is ample whitespace on wide screens is jarring.
*   **The Fix:** Removed all JavaScript-driven layout shifting and body padding logic. The TOC sidebar was converted into a pure floating overlay (`z-index: 120`). The main document remains completely isolated and perfectly centered in the viewport at all times.
